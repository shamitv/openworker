# Phase 5 — Temporary internet deployment and verification

## Implementation

Document a fresh Linux VM setup with the built SPA, Python package, OpenShell and administrator-provisioned username/password accounts. Expose it temporarily through Cloudflare Quick Tunnel: browser → Cloudflare HTTPS edge → `cloudflared` on the VM → loopback web gateway → private engines → OpenShell. The gateway and every engine listen only on loopback. Cloudflare supplies public TLS; the default deployment requires no custom domain, Nginx public listener or VM certificate. Retain the Nginx instructions and evidence for the existing local HTTPS fixtures.

Run `cloudflared tunnel --url http://127.0.0.1:8766` in a supervised terminal, obtain the generated HTTPS URL, then start `openworker-web serve` with that exact `--public-origin`. Preserve password sessions, CSRF/origin checks and engine authentication. Use normal browser and CLI certificate verification, without test certificate exceptions or a custom fixture CA. Keep the tunnel alive for the acceptance session; automatic tunnel lifecycle management is outside this revision.

Document manual tunnel restart recovery: stop the old gateway and joiner processes, start the new tunnel, update the gateway's public origin using the same data directory, and sign in at the new hostname. Generate fresh account join URLs and rerun `openworker join` using each machine's existing state, preserving its identity and updating its saved controller URL. Verify that subsequent `openworker up` reconnects to the new URL with the same machine ID.

Add a public-tunnel acceptance variant of the existing hosted browser gate. Run independent Chromium/Alice and Firefox/Bob sessions with real private engines and OpenShell, approved work, workspace boundaries, exact browser downloads, persistence and external workstation machine connections. Extend checks to sessions, secrets, inbox, approvals, files, account revocation, browser/machine WebSockets, CSRF/origin rejection, login throttling and forwarded client identity. Exercise sandbox failure, crash recovery and unattended scheduled work. Verify existing desktop authentication and Tauri behavior.

Document backup/restore of the gateway database and per-user homes, private process logs, health checks and resource measurements for the target of 20 resident engines. Record the tunnel hostname, versions, commands and results; retain sanitized logs and private browser traces. Stop and remove disposable deployment and joiner state after acceptance. External OAuth consent, callback configuration and token exchange are outside this multi-phase plan; preserve existing implementation and historical tests. No new authentication API or database migration is required.

## Acceptance

A fresh VM deployment can be followed from documentation using its generated Quick Tunnel URL and existing sandbox setup. Public HTTPS passes ordinary certificate verification. Both accounts remain isolated, the external machine uses account-scoped WSS, and tunnel restart recovery preserves account data and machine identity. The multi-user security, operational recovery and desktop regression checks pass; the public gate has no skipped scenarios or automatic retries. Record actual results and cleanup in `status.md` before marking this phase complete. Phases 1–4 keep their recorded completion scope; the separate Windows sandbox gate remains pending.

Quick Tunnel hostnames change on restart, have no uptime guarantee, permit at most 200 in-flight requests and do not support SSE. The hosted UI uses WebSockets; verify them through the tunnel. This acceptance establishes supervised temporary internet access, with no claim of stable production hosting. See [Cloudflare's Quick Tunnel documentation](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).
